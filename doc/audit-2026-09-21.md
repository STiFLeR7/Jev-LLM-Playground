# Reference-project readiness audit

Date: 2026-09-21. Scope: local working tree, official documentation, offline tests, and saved synthetic results. No application changes, paid requests, commits, or pushes were performed during this audit.

## Verdict

Good local experiment; not yet a reference-project release. Preserve the small dependency-free architecture. Prioritize response-boundary hardening, reproducible evidence, and a trace that explains application policy. A monorepo or general-purpose SDK is not justified by the current single task.

## Evidence checked

- `npm test`: six passed, zero failed, on the available Windows/Node environment.
- `npm run eval`: baseline 12/16, zero provider calls.
- `node --check server.mjs` and `node --check web/app.js`: passed.
- Recomputed the saved report with `summarize`: identical to its stored summary.
- Git origin is configured; HEAD has no commit and project files are untracked. `.env` is ignored; `.env.example` and the curated report are not ignored. Remote contents and GitHub settings were not inspected.
- Browser rendering, assistive-technology behavior, real timeout timing, and hosted CI were not verified. This is not an exhaustive security audit or secret scan. The actual key was not read.
- No graph index or installed graphify command was available; direct source inspection was used instead.

## Current architecture

```text
CLI arguments ──────────────────────┐
Browser → loopback HTTP server ─────┤
                                   ▼
                      playground.mjs requestBody
                                   ▼
                     evaluateTicket → TypeSafe HTTP
                                   ▼
                         validateResponse → route
                                   ▼
                       JSON / UI / saved evaluation

data/tickets.json → CLI evaluation → summarize
```

There is already a useful separation between model evaluation and deterministic routing, despite their sharing one module. Both entry points reuse it. No irreversible ticket operations exist. `fetchImpl` and the server's injected `evaluate` function make offline testing practical.

## Official contract check

The endpoint, bearer authentication, state/model/questions request, and model/answers/usage response match the current [API reference](https://docs.typesafe.ai/api). The project's four Choice options, three Score levels, and Noul without criteria are valid. Score is a probability-weighted level value; it is not necessarily an integer. Unknown-category and numeric-range guards are appropriate application checks, not evidence that semantic decisions are correct.

Choice/Score confidence summarizes a distribution; Noul has no separate confidence. Do not label confidence as measured accuracy or substitute it for the chosen option's probability. [Confidence documentation](https://docs.typesafe.ai/confidence)

The current model page lists `jev-1.13.0`, accepts versioned IDs, and warns that aliases move. Pin the version in benchmark configuration; keep `jev-latest` as a convenient interactive default. The listed price remains $0.042/M input tokens with output free. These are dated vendor facts, not an account billing verification. [Models](https://docs.typesafe.ai/models)

TypeSafe positions Jev as a System One model for structured software decisions. Architecture, parallel-sampling, and RLCD descriptions are vendor claims, not independently reproduced findings here. [Introduction](https://docs.typesafe.ai/introduction), [launch announcement](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

## Findings, ordered by release priority

### A1 — Medium: provider extras cross the output boundary

Evidence: `playground.mjs:39–63` validates required fields but returns the original object. `playground.mjs:100` forwards `answers` and `usage` wholesale. An offline mock containing `answers.extra.debug = 'SYNTHETIC_PRIVATE_MARKER'` preserved that marker in `evaluateTicket` output.

Impact: undocumented provider fields can enter browser JSON and saved reports. This is a demonstrated data-minimization gap, not evidence that the real key has leaked. Authentication is still server-side and error bodies are sanitized.

Action: construct a normalized allowlisted response, including nested answers/usage, and use it everywhere. Do not promise universal secret removal: legitimate input text and provider strings still require review before publication.

### A2 — Medium: contradictory Score data is accepted

Evidence: `playground.mjs:58` accepts a score of 2 with probabilities `{0:1,1:0,2:0}`. The mocked response passed validation. The documented weighted score would be 0.

Impact: the UI can display inconsistent information as validated. Frustration does not currently trigger routing, so this is not a demonstrated wrong-route bug.

Action: check score against the weighted distribution with an explicit rounding tolerance; cover exact, rounded, and contradictory responses. Do not invent a confidence formula that the docs do not specify.

### A3 — High for benchmark credibility: evidence is not yet frozen or diagnostic

Evidence: `playground.mjs:178` includes questions, split, model alias, threshold, and a dataset name, but no content hash, configuration schema version, policy version, baseline version, or code revision. `summarize` has aggregate metrics but no confusion matrix/per-class recall. Failed calls have no latency record. Dataset loading and iteration are embedded in CLI `main`.

The saved 16/16 result recomputes correctly. However, all department confidences are 0.91–1.00: the 0.8 low-confidence branch is never exercised by this live dataset. The four reviews follow the `other` rule. The data cannot demonstrate that confidence improved routing. Only the second of two passes was saved, so repeat consistency cannot be reconstructed. Urgency and frustration have no labels.

Action: preserve the historic artifact unchanged; introduce versioned configuration, content hashes, explicit run metadata, replay, and class-level metrics. Add separate development boundary cases before freezing any new test set. Do not rename the existing sample as a production benchmark or claim calibration.

### A4 — Medium: important behavior lacks regression evidence

Existing tests cover unknown choices, malformed fields, low confidence, review, common HTTP failures, preview, missing credentials, origin/host checks, and basic secret absence. Missing checks include abort-signal behavior, exactly one attempt on failure, concurrent-request rejection and lock release, normalized saved outputs, exact threshold equality, and browser interactions. A thrown mock connection error is not a timeout timing test.

Action: add focused behavioral checks, not a target test count. Keep zero retries for now and explicitly test that choice; retries would change costs and benchmark semantics.

### A5 — Medium: UI is an inspector, not yet a decision trace

Evidence: `web/app.js` shows the result, probabilities, and raw JSON, but does not narrate which policy condition caused routing/review. There is no recorded-result explorer. Inputs are disabled during requests and prior output is cleared when input changes, which are useful existing safeguards.

Action: expose a deterministic reason from the shared routing policy and render input, question types, validated observation, policy condition, and suggested action. Preserve urgency as Noul; the roadmap's illustrative urgency Score is not this implementation. Separate preview, recorded replay, and live labels. Never imply access to internal model reasoning.

### A6 — Release gate: documentation and publication state need alignment

README line 86 incorrectly says there is no remote. Browser startup sits under “Run a real ticket” even though preview is free. The first screen lacks clone instructions and an evidence summary. Research is dated historical material and should link clearly to later validation. `SECURITY.md`, dedicated contribution guidance, and a license file are absent. Package metadata intentionally says `UNLICENSED`.

Action: improve onboarding and evidence navigation, obtain the owner's license decision, and add contribution/security guidance with a real reporting channel. Do not call the project open source before choosing a license. No public release can be verified from local origin configuration alone.

## Next-release scope (proposed v0.2)

1. Accurate Jev learning entry point, current project-state wording, and security/contribution instructions.
2. A small support-routing Decision Bench: frozen config and hashes, offline replay, confusion matrix, per-class metrics, and failure accounting. Keep one task and one baseline initially.
3. One verified browser experience: application decision trace plus read-only access to the curated synthetic run, with clear provenance labels.

Constraints: Node >=22.9.0; no runtime dependencies; preserve existing CLI commands and saved historical report; local-only server; explicit live opt-in; no automatic retries; synthetic/public data only; no commits/pushes/paid runs without further authorization. License selection belongs to the owner.

Deferred: package workspaces, SDK/adapter framework, hosted accounts, database, three new demos, general-purpose LLM comparison, and promotion automation. Add a new backend or task only after its actual contract and evaluation labels are defined.

## Release gates

- Boundary regression tests and offline CLI/replay pass; existing commands remain compatible.
- New reports identify exact dataset/config/policy/model and keep failed attempts visible.
- Browser desktop/mobile, keyboard, loading, failure, preview, and recorded modes verified; screenshots use synthetic inputs.
- README claims link to evidence and keep vendor claims separate.
- Owner chooses license and private vulnerability-report channel.
- Review staged contents for secrets, run hosted CI after an authorized push, then approve a tag/release separately.

This audit completes the first roadmap item. API verification is complete for the current three-question contract, not every future recipe. Other launch items remain pending or partially implemented; six passing tests do not make the 20-item launch checklist complete.
